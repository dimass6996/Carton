# Carton — учебный roadmap Java Backend

**Цель:** разработать backend интернет-магазина на Java 21 и Spring Boot, постепенно освоив PostgreSQL, Spring Data JPA, Security, тестирование, транзакции, Kafka, Redis, Docker и CI/CD.

**Принципы:** модульный монолит, backend сначала (Swagger, frontend позже), две роли — покупатель и администратор, оплата через имитируемый сервис. Каждая задача рассчитана примерно на **1–2 вечера** (обычно 2–6 часов, но знакомство с новой темой может занять дольше). Делай задачи по порядку; там, где зависимости не линейны, они отмечены отдельно.

## Что делает Carton

- Покупатель просматривает и фильтрует каталог, оформляет заказ, имитирует оплату, видит историю и отменяет допустимые заказы.
- Администратор управляет товарами и остатками, просматривает заказы и меняет разрешённые статусы.
- Заказ хранит снимок цен на момент оформления и резервирует складские остатки.
- Успешная оплата подтверждает продажу, неуспешная оплата и отмена освобождают резерв.
- Kafka используется для вторичных событий (уведомлений), Redis — для кэширования каталога.

**Бизнес-инварианты:** `available = on_hand - reserved`; `on_hand >= reserved >= 0`; нельзя оформить заказ при нехватке товара; повторный запрос не дублирует заказ или списание; покупатель не видит чужие заказы.

**Состояния заказа:** `PENDING_PAYMENT → PAID → PROCESSING → COMPLETED`; из `PENDING_PAYMENT` возможны `CANCELLED` и `FAILED` (платёж не прошёл); отмена до завершения обработки — по явно определённым правилам. Возвраты и настоящие платежи не входят в первую версию.

**Основные сущности:** `User`, `Product`, `Inventory`, `Order`, `OrderItem`, `Payment`, позднее `OutboxEvent`, `Notification`.

## Этап 3. Заказы и склад

### - [ ] C-13. Спроектировать модель заказа
- **Теория:** 1:N, нормализация, `@OneToMany`/`@ManyToOne`, enum, агрегаты.
- **Практика:** `Order`, `OrderItem`, внешние ключи и миграция.
- **Критерии готовности:** заказ хранит несколько позиций и их связи корректны.
- **Изучишь:** реляционное моделирование предметной области.
- **Зависимости:** C-12.

### - [ ] C-14. Создание заказа
- **Теория:** сервисные операции, DTO, `@Transactional`, атомарность.
- **Практика:** `POST /api/v1/orders`, вычисление суммы сервером, сохранение `PENDING_PAYMENT`.
- **Критерии готовности:** несколько позиций сохраняются атомарно; ошибки откатывают операцию.
- **Изучишь:** бизнес-транзакции между таблицами.
- **Зависимости:** C-13; позднее дополнить резервированием из C-17.

### - [ ] C-15. Фиксация цены при покупке
- **Теория:** snapshots, immutable history, точность денежных вычислений.
- **Практика:** записывать цену в `OrderItem` при оформлении.
- **Критерии готовности:** изменение `Product.price` не меняет стоимость прежних заказов.
- **Изучишь:** исторические данные и денежные суммы.
- **Зависимости:** C-14.

### - [ ] C-16. Складские остатки
- **Теория:** инварианты, CHECK constraints, Inventory.
- **Практика:** `Inventory` с `on_hand` и `reserved`, пополнение склада администратором (авторизация добавится позже).
- **Критерии готовности:** `on_hand >= reserved >= 0`, доступный остаток рассчитывается правильно.
- **Изучишь:** складскую модель и ограничения БД.
- **Зависимости:** C-15.

### - [ ] C-17. Резервирование товара
- **Теория:** атомарные SQL updates, транзакции, race conditions.
- **Практика:** встроить резервирование в оформление заказа, проверять доступный остаток.
- **Критерии готовности:** нехватка товара не создаёт неполный заказ или частичный резерв.
- **Изучишь:** согласованное изменение состояния.
- **Зависимости:** C-14, C-16.

### - [ ] C-18. Получение заказов
- **Теория:** JPQL, lazy loading, DTO projections, N+1.
- **Практика:** получение заказа и постраничного списка с позициями; права добавятся позже.
- **Критерии готовности:** позиции, суммы, статусы корректны; страницы работают.
- **Изучишь:** загрузку связей и работу Hibernate.
- **Зависимости:** C-17.

### - [ ] C-19. Отмена заказа
- **Теория:** конечные автоматы, транзакционные переходы, инварианты.
- **Практика:** отмена неоплаченного заказа с освобождением резерва.
- **Критерии готовности:** повтор не освобождает резерв дважды; завершённый заказ отменить нельзя.
- **Изучишь:** правила переходов состояний.
- **Зависимости:** C-18.

### - [ ] C-20. Тесты оформления заказа
- **Теория:** тесты бизнес-правил, параметризация, граничные значения.
- **Практика:** тесты остатков, отмены, цены и ошибочного количества.
- **Критерии готовности:** ключевые правила автоматически проверены.
- **Изучишь:** тестирование доменной логики.
- **Зависимости:** C-19.

## Этап 4. Пользователи, оплата и MVP

### - [ ] C-21. Пользователи и роли
- **Теория:** аутентификация vs авторизация, роли, хеширование паролей.
- **Практика:** `User`, `CUSTOMER`/`ADMIN`, миграции и локальные тестовые аккаунты с хешами.
- **Критерии готовности:** пользователи и роли в БД, пароли не хранятся в открытом виде.
- **Изучишь:** модели аккаунтов и базовую безопасность.
- **Зависимости:** C-20.

### - [ ] C-22. Spring Security

- **Практика:** защитить API, локально использовать HTTP Basic (только при защищённом соединении вне локальной среды).
- **Критерии готовности:** анонимный пользователь не оформляет заказ; покупатель не меняет каталог.
- **Изучишь:** Spring Security и RBAC.
- **Зависимости:** C-21.

### - [ ] C-23. Привязка заказов к покупателю
- **Теория:** security context, ownership, IDOR.
- **Практика:** связать `Order` с `User`, ограничить просмотр и отмену чужих заказов.
- **Критерии готовности:** покупатель A не видит заказ B, администратор видит все.

- **Зависимости:** C-22.

### - [ ] C-24. Модель оплаты
- **Теория:** статусы платежей, связи, технические и бизнес-ошибки.
- **Практика:** `Payment`, миграция, контракт fake provider.
- **Критерии готовности:** попытка оплаты сохраняется и читается.
- **Изучишь:** границы бизнес-модуля.
- **Зависимости:** C-23.

### - [ ] C-25. Имитация оплаты
- **Теория:** interfaces, dependency inversion, test doubles, deterministic testing.
- **Практика:** имитировать успех и отказ по контролируемому тестовому сценарию.
- **Критерии готовности:** оба варианта доступны без реальных денег и внешнего провайдера.
- **Изучишь:** заменяемые интеграции.
- **Зависимости:** C-24.

### - [ ] C-26. Обработка результата оплаты
- **Теория:** ACID, транзакционные переходы, повторные результаты.
- **Практика:** при успехе `PAID`, уменьшить `on_hand` и `reserved` на купленное количество; при отказе `FAILED`, освободить резерв.
- **Критерии готовности:** повторная обработка результата не списывает остаток ещё раз.
- **Изучишь:** согласованность платежей и склада.
- **Зависимости:** C-25, C-17.

### - [ ] C-27. Обработка заказа администратором
- **Теория:** state machine, авторизация бизнес-операций.
- **Практика:** `PAID → PROCESSING → COMPLETED` только для администратора.
- **Критерии готовности:** нельзя обрабатывать неоплаченный заказ или пропускать статусы.
- **Изучишь:** защищённые переходы состояний.
- **Зависимости:** C-26.

### - [ ] C-28. Интеграционные тесты и MVP
- **Теория:** Testcontainers, unit vs integration tests.
- **Практика:** сквозные тесты с PostgreSQL для успешной и неудачной покупки.
- **Критерии готовности:** тесты проверяют реальные изменения БД и запускаются воспроизводимо.
- **Изучишь:** интеграционное тестирование Spring Boot.
- **Зависимости:** C-27.

**Веха: MVP.** Каталог, товары, остатки, аккаунты, заказы и имитация оплаты работают локально.

## Этап 5. Конкурентность и надёжность

### - [ ] C-29. Конкурентное резервирование
- **Теория:** race conditions, isolation levels, optimistic/pessimistic locking, atomic updates.
- **Практика:** параллельный интеграционный тест: 10 покупателей претендуют на последний товар; доработать резервирование при необходимости.
- **Критерии готовности:** один успешный резерв, без отрицательных остатков.
- **Изучишь:** защиту от overselling.
- **Зависимости:** C-28.

### - [ ] C-30. Идемпотентность создания заказов
- **Теория:** retry, idempotency key, unique constraints, atomicity.
- **Практика:** `Idempotency-Key` с привязкой к покупателю и параметрам запроса.
- **Критерии готовности:** повтор не создаёт второй заказ; иной запрос с тем же ключом отклоняется.
- **Изучишь:** идемпотентные HTTP-операции.
- **Зависимости:** C-29.

### - [ ] C-31. Автоматическое истечение резервов
- **Теория:** `@Scheduled`, TTL, транзакции, идемпотентность фоновых задач.
- **Практика:** время истечения резерва и отмена просроченных неоплаченных заказов.
- **Критерии готовности:** просроченные резервы освобождаются однократно; оплаченные заказы не затронуты.
- **Изучишь:** периодические процессы и согласование по времени.
- **Зависимости:** C-30.

### - [ ] C-32. Оптимизация SQL
- **Теория:** indexes, `EXPLAIN ANALYZE`, N+1, fetch strategies.
- **Практика:** собрать демонстрационные данные, измерить запросы к списку заказов, исправить N+1 и добавить индексы.
- **Критерии готовности:** зафиксированы измерения и объяснён план выполнения SQL.
- **Изучишь:** производительность Hibernate/PostgreSQL.
- **Зависимости:** C-31.

## Этап 6. Kafka и события

### - [ ] C-33. Kafka: первое событие
- **Теория:** broker, topic, partition, offset, consumer group, producer/consumer.
- **Практика:** Kafka в Compose, Spring Kafka, учебное сообщение.
- **Критерии готовности:** сообщение видно у consumer.
- **Изучишь:** транспорт асинхронных событий.
- **Зависимости:** C-32.

### - [ ] C-34. События заказов
- **Теория:** event-driven architecture, event contract, commit boundaries.
- **Практика:** `OrderPaidEvent` после коммита оплаты (пока без гарантированного outbox).
- **Критерии готовности:** после оплаты появляется корректное событие с event ID и order ID.
- **Изучишь:** проектирование событий и границы транзакции.
- **Зависимости:** C-33, C-26.

### - [ ] C-35. Consumer уведомлений
- **Теория:** `@KafkaListener`, consumer groups, at-least-once delivery.
- **Практика:** consumer в том же приложении; записывать `Notification` в PostgreSQL.
- **Критерии готовности:** оплата приводит к записи уведомления без синхронного вызова из payment service.
- **Изучишь:** обработку событий и слабую связанность.
- **Зависимости:** C-34.

### - [ ] C-36. Повторы и ошибки Kafka
- **Теория:** retries, offsets, dead-letter topic, идемпотентный consumer.
- **Практика:** дедупликация по event ID, ограниченные retry и DLT.
- **Критерии готовности:** повтор события не дублирует уведомление; неисправимое событие попадает в DLT.
- **Изучишь:** устойчивую обработку сообщений.
- **Зависимости:** C-35.

### - [ ] C-37. Transactional Outbox
- **Теория:** dual-write problem, transactional outbox, eventual consistency.
- **Практика:** `outbox_events`, запись события в той же транзакции, что оплата; отдельный publisher в Kafka.
- **Критерии готовности:** при отключённой Kafka оплата сохраняется, а событие публикуется после восстановления.
- **Изучишь:** надёжную связь БД и Kafka.
- **Зависимости:** C-36. **Примечание:** задача может потребовать разделения на два вечера (сохранение outbox и publisher). Outbox вместе с идемпотентным consumer нужен, поскольку повторы доставки всё равно возможны.
